## 1. Что требуется

| № | Требование из задачи |
| --- | --- |
| Т1 | Объект (например, УГО светильника) хранит **несколько** спецификаций и **несколько** соединений; их число заранее неизвестно. |
| Т2 | Программное добавление соединения (спецификации) — «при желании», то есть по запросу, а не автоматически. |
| Т3 | Программное удаление **последнего** соединения (спецификации). |
| Т4 | Ручное управление ими в панели. |
| Т5 | Вид: «Спецификация №1» — группа, внутри `spec_1_pos`, `spec_1_Name`, `spec_1_col`; «Спецификация №2» — группа, внутри `spec_2_pos`, `spec_2_Name`, `spec_2_col`; так же соединения. |

Пример из задачи, используемый ниже:

```text
УГО светильника
  Спецификация №1 — светильник (корпус)
  Спецификация №2 — лампа
  Спецификация №3 — клеммная колодка
  Соединение №1   — ЩО1.1
  Соединение №2   — выключатель
```

## 2. Что уже есть в плагине

Варианты опираются на уже реализованное ([TZXDATA](../TZXDATA.md), [xdata-v2.md](xdata-v2.md),
[vst-editing.md](vst-editing.md)):

- **Тип `Table`** (TZXDATA 4.2): упорядоченный список строк, колонки — параметры схемы. В XDATA строка —
  вложенный список `(1002 . "{") … (1002 . "}")`. Ключ строки — колонка `key` (или первая `String`).
  В VST: `+ Добавить` (для ключа `Integer` новый ключ — `max + 1`), `×` удаляет строку, `✎` раскрывает
  ячейки строки как дочерние строки с редакторами. Операции Core — `SelectionEdit.AddTableRow` и
  `SelectionEdit.DeleteTableRow`; при групповом редактировании строки сопоставляются по ключу.
- **Группы**: поле `group` параметра — заголовок группы в VST. Параметры **вне шаблона** объекта
  показываются в группе «Дополнительные» (TZXDATA 6.6), объект **без шаблона** показывает
  записанные значения в группах их параметров.
- **`CalculatedString`** не может ссылаться на `Table`: ссылка даёт ошибку
  «таблица … не подставляется» (`CalculatedStrings.cs`).
- **Лимиты**: строка `1000` — не больше 255 байт, весь XDATA объекта — не больше 16 383 байт
  (`XDataV2.MaxXDataBytes`); `Id` — `[A-Za-z_][A-Za-z0-9_]{0,63}`, регистр не учитывается.

Проба `Issue61Probe` проверила на текущем Core:

| Факт | Результат |
| --- | --- |
| A: строка таблицы подписана **значением ключа** (`1`, `2`, `3`), а не «Спецификация №1»; в колонке «Значение» — вторая колонка таблицы (`Spec_Name`) | подтверждено |
| A: «добавить» = `AddTableRow` с ключом `max + 1`; «удалить последнее» = `DeleteTableRow(max)` | подтверждено: соединения 1, 2 → 1, 2, 3 → 1, 2 |

## 3. Варианты

### Вариант A. Табличный параметр `Table` (есть сейчас, доработки небольшие)

Спецификация и соединения — две таблицы. Номер записи — ключевая колонка `Integer`.

```json
{ "id": "Specs", "type": "Table", "caption": "Спецификация", "group": "Спецификация",
  "columns": [ "Spec_No", "Spec_Name", "Spec_Count", "Spec_Pos", "Spec_Unit" ], "key": "Spec_No" },
{ "id": "Connections", "type": "Table", "caption": "Соединения", "group": "Соединения",
  "columns": [ "Conn_No", "Conn_Target", "Conn_Cable", "Conn_TargetId" ], "key": "Conn_No" }
```

```text
(1000 . "Specs") (1002 . "{")
    (1002 . "{") (1000 . "Spec_No") (1071 . 1) (1000 . "Spec_Name") (1000 . "Светильник (корпус)") (1000 . "Spec_Count") (1040 . 1.0) (1002 . "}")
    (1002 . "{") (1000 . "Spec_No") (1071 . 2) (1000 . "Spec_Name") (1000 . "Лампа")               (1000 . "Spec_Count") (1040 . 2.0) (1002 . "}")
(1002 . "}")
```

- **Т1** — да, сейчас. **Т4** — сейчас: `+ Добавить` (№ = max + 1), `×`, `✎`; групповое редактирование.
- **Т2/Т3** — операции Core уже есть (проба выше); нужна только обёртка — команда и функция LISP
  (раздел 4).
- **Т5** — частично. Сейчас строка подписана ключом «1», а не «Спецификация №1», поля видны после `✎`.
  Доработка: поле схемы таблицы `rowCaption` (например `"Спецификация №{Spec_No}"`) и раскрытие
  строки как группы. Внутренние `Id` полей — общие для всех строк (`Spec_Name`), а не `spec_1_Name`.

Плюсы: уже работает; одна таблица на любое число записей; добавление новых колонок — только схемой.
Минусы: нельзя сослаться на ячейку в `CalculatedString` (`@@[spec_1_Name]` невозможно, нужен новый
синтаксис вроде `@@[Specs#1.Spec_Name]`); внешней программе на LISP нужно разбирать вложенные списки;
`Id` вида `spec_1_pos` не появляются нигде.

### Вариант B. Повторяющаяся группа — новый тип `Repeat` (рекомендуется)

Схема описывает поля **один раз**, а в объекте хранится столько экземпляров, сколько нужно. `Id`
экземпляра строится по правилу `<id>_<n>_<поле>` — ровно как в задаче: `spec_1_pos`, `spec_1_Name`,
`spec_1_col`.

```json
{ "id": "spec", "type": "Repeat", "caption": "Спецификация №{n}", "group": "Спецификация",
  "fields": { "pos": "Spec_Pos", "Name": "Spec_Name", "col": "Spec_Count" } },
{ "id": "conn", "type": "Repeat", "caption": "Соединение №{n}", "group": "Соединения",
  "fields": { "target": "Conn_Target", "cable": "Conn_Cable" } }
```

`fields` сопоставляет суффикс `Id` с обычным параметром схемы, у которого берутся тип, подпись,
единица, `Min/Max`, ENUM и умолчание (как колонки `Table`). XDATA — **плоские пары**, без вложенных
списков:

```text
(1000 . "spec_1_pos")  (1000 . "1")
(1000 . "spec_1_Name") (1000 . "Светильник (корпус)")
(1000 . "spec_1_col")  (1040 . 1.0)
(1000 . "spec_2_pos")  (1000 . "2")
(1000 . "spec_2_Name") (1000 . "Лампа")
(1000 . "spec_2_col")  (1040 . 2.0)
(1000 . "conn_1_target") (1000 . "ЩО1.1")
(1000 . "conn_2_target") (1000 . "Выключатель")
```

Правила:

- **Число экземпляров** — наибольший `n`, найденный в XDATA; отдельный счётчик не хранится (его нельзя
  рассинхронизировать).
- **Добавить** — записать все поля экземпляра `n = max + 1` со значениями по умолчанию (как «+ Параметр»
  пишет умолчание), поэтому пустая группа «Спецификация №4» сразу видна.
- **Удалить последний** — удалить все пары `spec_<max>_*` одной транзакцией.
- **Удалить из середины** — со сдвигом номеров (`spec_3_*` → `spec_2_*`) одной транзакцией и одним Undo
  (по умолчанию) или с пропуском номера; выбор — вопрос к заказчику (раздел 8).
- **Формулы**: `@@[spec_1_Name]` работает как ссылка на обычный параметр (тип берётся из поля
  `Spec_Name`); при желании — агрегаты `@@[spec:count]`, сумма `col`.
- **Групповое редактирование**: `spec_2_Name` у нескольких объектов сравнивается как обычный параметр;
  экземпляр, которого нет у части объектов, — «Разное».
- **Проверки схемы**: `Id` вида `spec_<число>_<суффикс>` не может совпадать с обычным параметром,
  полная длина `Id` — не больше 64 символов, номер — например, не больше 999; поле `Repeat` не может
  быть `Table` или `Repeat`.

- **Т1–Т5** — да, полностью, включая имена `spec_1_pos` из задачи.

Плюсы: точный вид и имена из задачи; формулы и внешние программы читают плоские пары
(`(cdr (assoc "spec_1_Name" …))`) без разбора вложенных списков; групповое редактирование и проверки
работают как для скалярных параметров; формат XDATA v2 не меняется (это обычные пары `Id` + значение,
старые версии плагина покажут их в «Не описаны в схеме», не потеряв).
Минусы: нужен код — новый тип в схеме, распознавание `Id` по правилу, построение групп VST, операции
добавления/удаления, редактор схемы (оценка — 4–6 этапов, раздел 7); сдвиг номеров при удалении
из середины меняет `Id`, на которые могут ссылаться формулы.

### Вариант C. Фиксированный набор пронумерованных параметров (без кода, работает сейчас)

В схеме заранее объявляются `spec_1_pos` … `spec_N_col` с группами «Спецификация №1» …
«Спецификация №N» — [examples/issue61-numbered-schema.json](../examples/issue61-numbered-schema.json)
(N = 5).

- **Т5** — да, по виду и именам. **Т1** — только до N, заданного в схеме.
- **Т4** — «+ Параметр» добавляет **одно поле** за раз (`spec_2_pos`, затем `spec_2_Name` …), `×` удаляет
  одно поле. **Т2/Т3** — `SetParameter`/`RemoveParameter` каждого поля (проба выше) или LISP `entmod`.
- Проба показала ограничение: у объекта **с шаблоном** экземпляры вне шаблона попадают в
  «Дополнительные», а не в «Спецификация №2». Обходы: объекты без шаблона (группы правильные) или
  шаблон со всеми N экземплярами (тогда пустые группы видны с `○`).

Плюсы: работает сегодня, ничего не нужно программировать; формулы `@@[spec_1_Name]` работают.
Минусы: предел N; схема растёт (N × число полей, меню «+ Параметр» длинное); удаление «последней»
делается вручную по полям. Подходит как **временное решение**, а его данные без переноса
читаются вариантом B (те же `Id`).

Небольшая доработка, полезная и для B: показывать параметры вне шаблона в **их собственной группе**
схемы, если она задана, а не в «Дополнительных».

### Вариант D. Записи в словаре расширения объекта (XRecord)

Каждая спецификация и каждое соединение — отдельный `Xrecord` в словаре расширения примитива:
`ExtensionDictionary/VELEC_ITEMS/SPEC/0001`, `…/CONN/0002`. Внутри — те же пары `Id` + значение.

Плюсы: нет общего лимита XDATA 16 КБ на объект (у каждого `Xrecord` свой объём);
изменение одной записи — один `Xrecord`; `COPY` копирует словарь расширения вместе с примитивом.
Минусы: второе место хранения рядом с XDATA v2 — новый читатель, кэш, писатель, перенос и проверка;
чтение выделения медленнее (открытие словаря каждого объекта); внешним программам нужен `dictsearch`.
Оправдан, только если записей больше ~100 на объект или нужны длинные тексты; для светильника с
3 спецификациями и 2 соединениями — избыточен.

### Вариант E. Соединение — ссылка на объект по `DEVICE_ID` (дополнение к A, B или D)

«ЩО1.1» и «выключатель» — тоже объекты чертежа. Вместо текста соединение может хранить их
`DEVICE_ID` (GUID — TZXDATA 6.4 прямо предназначает его «ключом для будущих связей между объектами»):

```text
(1000 . "conn_1_target") (1000 . "3F2504E0-4F89-11D3-9A0C-0305E82C3301")   ; DEVICE_ID щита
```

- VST показывает обозначение цели (её `GC_Name` или выбранный параметр), кнопка «⌖ Указать» выбирает
  объект в чертеже, «Показать» подсвечивает его.
- Удалённая цель — `!` в VST и пункт `VELEC_CHECK`; дубли `DEVICE_ID` после `COPY` уже находит
  `VELEC_CHECK`.
- Переименование щита сразу меняет подпись всех соединений с ним; по ссылкам строится отчёт
  «что к чему подключено».

Нужен новый тип (`Link`), индекс `DEVICE_ID → ObjectId` чертежа и выбор объекта. Текстовое соединение
(как сейчас в задаче) остаётся допустимым: тип выбирается в схеме для каждого поля. Аналог для
спецификации — ссылка на позицию каталога изделий (ENUM или каталог в NOD) вместо ввода наименования.

## 4. Программное добавление и удаление (общее для A, B, C)

Предлагается три уровня, каждый — поверх предыдущего; все пишут через `XDataWriter` одной транзакцией
с проверкой лимитов, один шаг Undo.

1. **API Core** (для других модулей .NET):
   `SelectionEdit.AddItem(collection, values)` — добавить запись `max + 1` с заданными полями (остальные —
   умолчания); `SelectionEdit.RemoveLastItem(collection)` — удалить запись с наибольшим номером.
   Для варианта A это обёртки над существующими `AddTableRow`/`DeleteTableRow`, для C — над
   `SetParameter`/`RemoveParameter`. При выделении нескольких объектов «последняя» — **своя у каждого
   объекта** (у светильника с 3 соединениями удаляется №3, у соседнего с 2 — №2).
2. **Команды** (для кнопок модуля меню, скриптов и макросов) с `UsePickSet`:
   - `VELEC_ITEM_ADD` — запрашивает коллекцию `[Спецификация/Соединение]`, затем поля по очереди
     (Enter — умолчание): `^C^C_VELEC_ITEM_ADD _Соединение ЩО1.1 ;`;
   - `VELEC_ITEM_REMOVE_LAST` — запрашивает коллекцию и удаляет последнюю запись у каждого объекта,
     в командной строке — «Удалено: Соединение №2 (2 объекта)».
3. **Функции LISP** (`[LispFunction]` в проекте AutoCAD), чтобы «при желании» добавлять из своих программ:

   ```lisp
   (velec-item-add ent "conn" '(("target" . "ЩО1.1")))   ; → 3, номер новой записи
   (velec-item-remove-last ent "conn")                  ; → 3, номер удалённой, или nil
   (velec-item-count ent "conn")                        ; → 2
   (velec-item-get ent "spec" 2)                        ; → (("pos" . "2") ("Name" . "Лампа") ("col" . 2.0))
   ```

Без плагина данные можно менять и обычным `entget`/`entmod`, но тогда не проверяются типы, 255 байт
и 16 КБ, а для варианта A надо самостоятельно собирать вложенные списки — для программ лучше функции
LISP выше.

Автоматически ничего не добавляется («при желании»). Необязательно: `minItems` в шаблоне (например,
`"minItems": { "spec": 1 }`) создаёт «Спецификация №1» при назначении шаблона.

## 5. Ручное управление в панели (VST)

Для варианта B (и для A с доработкой `rowCaption`) коллекция — узел-группа со счётчиком и
`+ Добавить`, каждая запись — вложенная группа «Спецификация №N» с полями:

```text
┌────┬───────────────────────┬─────────────────────┬───┬──────────────┐
│    │ ПАРАМЕТР              │ ЗНАЧЕНИЕ            │ ● │ ПРИМЕЧАНИЕ   │
├────┼───────────────────────┼─────────────────────┼───┼──────────────┤
│    │ ▾ Спецификация        │ 3 записи            │   │ [+ Добавить] │
│ ×  │   ▾ Спецификация №1   │ Светильник (корпус) │   │              │
│    │       Позиция         │ 1                   │ ● │ spec_1_pos   │
│    │       Наименование    │ Светильник (корпус) │ ● │ spec_1_Name  │
│    │       Кол.            │ 1                   │ ● │ spec_1_col   │
│ ×  │   ▸ Спецификация №2   │ Лампа               │   │              │
│ ×  │   ▸ Спецификация №3   │ Клеммная колодка    │   │              │
│    │ ▾ Соединения          │ 2 записи            │   │ [+ Добавить] │
│ ×  │   ▸ Соединение №1     │ ЩО1.1               │   │ [⌖]          │
│ ×  │   ▸ Соединение №2     │ Выключатель         │   │ [⌖]          │
└────┴───────────────────────┴─────────────────────┴───┴──────────────┘
```

- `+ Добавить` — запись `max + 1` с умолчаниями, раскрыта, курсор в первом поле.
- `×` у записи — удалить её; у последней — сразу, у средней — по выбранному правилу нумерации.
- Контекстное меню коллекции: «Добавить», «Удалить последнюю»; записи — «Дублировать», «Вверх»,
  «Вниз» (перестановка — обмен номерами одной транзакцией).
- В колонке «Значение» свёрнутой записи — её главное поле (наименование/цель), чтобы список читался
  без раскрытия.
- Несколько объектов: записи сравниваются по номеру, различия — «Разное», как сейчас.
- Фильтр и `⊞/⊟` работают и на записях; раскрытие запоминается по шаблону.

## 7. Рекомендация

1. **Целевое решение — вариант B** (`Repeat`) для спецификаций и соединений, с программным слоем
   раздела 4 и панелью раздела 5. Он единственный выполняет Т1–Т5 буквально, включая имена
   `spec_1_pos`/`spec_1_Name`/`spec_1_col`, не меняет формат XDATA v2 и оставляет формулы и внешние
   программы на плоских парах.
2. **Для соединений — дополнительно вариант E**: поле `target` типа `Link` (ссылка по `DEVICE_ID`),
   когда объект подключения есть в чертеже; текст — когда нет.
3. **Сейчас, до разработки** — вариант C по
   [examples/issue61-numbered-schema.json](../examples/issue61-numbered-schema.json) (объекты без шаблона
   или шаблон со всеми экземплярами): его `Id` совпадают с B, поэтому данные потом не переносятся.
   Если формулы по записям и имена `spec_N_*` не нужны, вместо B достаточно варианта A
   ([examples/issue61-table-schema.json](../examples/issue61-table-schema.json)) с доработкой `rowCaption`
   и командами раздела 4 — это самый дешёвый путь.
4. Вариант D — только если окажется, что записей больше ~100 на объект или нужны длинные тексты.

Если выбран B, порядок работ (каждый — отдельная задача с тестами, как этапы TZXDATA):

1. Тип `Repeat` в модели схемы, JSON, NOD и проверках раздела 4.5.
2. Распознавание `Id` экземпляров в XDATA v2 и кэше значений, ссылки `@@[spec_1_Name]` в формулах.
3. VST: группы коллекций и записей, `+ Добавить`, `×`, «Удалить последнюю», групповое редактирование.
4. API Core, команды `VELEC_ITEM_ADD`/`VELEC_ITEM_REMOVE_LAST`, функции LISP.
5. Редактор схемы: создание `Repeat`, выбор полей; `VELEC_CHECK` — пропуски номеров, лишние поля.
6. (E) Тип `Link`, выбор объекта в чертеже, индекс `DEVICE_ID`, отчёт связей.

## 8. Вопросы к заказчику

| Вопрос | Предложение по умолчанию |
| --- | --- |
| Удаление записи из середины: сдвигать номера или оставлять пропуск? | Сдвигать одной транзакцией; формулы с `spec_3_*` отмечать в отчёте. |
| Выделено несколько объектов: «последняя» — своя у каждого или общий номер? | Своя у каждого объекта. |
| Соединение — текст или ссылка на объект чертежа? | Ссылка, если объект есть в чертеже (вариант E), иначе текст. |
| Нужен ли порядок записей (вверх/вниз)? | Да, обменом номеров. |
| Нужны ли итоги по записям (число, сумма `col`, список соединений) в формулах? | Да, после этапа 2 варианта B. |
| Нужно ли ограничение числа записей? | Нет, кроме лимита 16 КБ XDATA (~110 записей). |
| Имена `Id`: `spec_1_Name` (как в задаче) — регистр важен? | `Id` в плагине без учёта регистра; хранится как в схеме. |
