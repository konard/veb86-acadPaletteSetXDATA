# XDATA объекта в формате BobrovXDATA v2 и кэш значений (TZXDATA, этап 3)

Этап 3 из [TZXDATA](../TZXDATA.md): значения параметров схемы (этапы 1–2, [schema-nod.md](schema-nod.md))
хранятся в XDATA объекта парами «`Id` + типизированное значение» (раздел 6). Разбор, запись,
проверки лимитов и кэш значений реализованы в `Core` и тестируются без AutoCAD; транзакция
AutoCAD (`AutoCadXDataWriteTransaction`) не изменилась. Сторонние DLL не нужны.

| Файл | Назначение |
| --- | --- |
| `src/AcadPaletteSetXData.Core/XDataV2.cs` | Определение формата, разбор в `ObjectValues`, оценка размера, дубли `DEVICE_ID`. |
| `src/AcadPaletteSetXData.Core/XDataPatchV2.cs` | Изменение одной пары или одной строки `Table` без потери остальных данных. |
| `src/AcadPaletteSetXData.Core/ParameterTypes.cs` | Код группы, чтение, приведение и запись значения для каждого типа (`IParameterType`). |
| `src/AcadPaletteSetXData.Core/ObjectValuesCache.cs` | Кэш значений документа: LRU на 10 000 объектов, счётчик разборов. |
| `src/AcadPaletteSetXData.Core/SelectionEdit.cs` | Операции v2: параметр, удаление, ячейка/строка таблицы, шаблон, новый `DEVICE_ID`. |
| `src/AcadPaletteSetXData.Core/XDataWriter.cs` | Проверка 255 байт и 16 КБ у всех объектов до записи, сброс кэша записанных объектов. |
| `src/AcadPaletteSetXData.AutoCAD/AutoCadSchemaCaches.cs` | Кэш значений рядом с кэшем схемы документа. |
| `tests/AcadPaletteSetXData.Core.Tests/XDataV2Tests.cs` | Приёмочные тесты этапа. |
| `examples/tzxdata-stage3-v2.lsp` | `VELECV2SAMPLE` и `VELECXDATA` для ручной проверки в AutoCAD. |

## Формат

```text
(1001 . "BobrovXDATA")
(1070 . 2)                                  ; FMT — версия формата
(1000 . "DEVICE_ID") (1000 . "3F2504E0-4F89-11D3-9A0C-0305E82C3301")
(1000 . "TEMPLATE")  (1000 . "DEVICE")
(1000 . "Device_Type") (1000 . "Щит")       ; String, Enum (ключ), CalculatedString
(1000 . "Power")       (1040 . 2.5)         ; Double
(1000 . "Poles")       (1071 . 3)           ; Integer, 32 бита
(1000 . "InSpec")      (1070 . 1)           ; Boolean 0/1
(1000 . "Materials") (1002 . "{")           ; Table: строка — вложенный список пар
    (1002 . "{") (1000 . "Mat_Mark") (1000 . "CD35") (1000 . "Mat_Count") (1040 . 2.0) (1002 . "}")
(1002 . "}")
```

`XDataV2.FormatOf` различает форматы по первому значению после `(1001 . "BobrovXDATA")`:

| Первое значение | Формат | Поведение |
| --- | --- | --- |
| нет раздела или раздел пуст | `None` | v2-запись создаёт раздел с `(1070 . 2)`. |
| `(1070 . 2)` | `V2` | Разбор и запись этого этапа. |
| `(1070 . N)`, `N > 2` | `Newer` | Только чтение с предупреждением; запись отклоняется. |
| что-либо другое | `V1` | Строки `ключ=значение` этапов 3–5 (`XDataParser`); v2-запись отклоняется до переноса `VELEC_MIGRATE` (этап 9, [migration-check.md](migration-check.md)). |

Поля v1 (`SelectionEdit.Header`/`MaterialField`) не записываются в объект v2, а `XDataParser`
не проецирует пары v2 в поля v1 (строка `"Name=…"` в значении `String` не становится полем «Название»).

Системные `Id` (`DEVICE_ID`, `TEMPLATE`; `FMT` зарезервирован) — строки `1000`. При записи они
стоят первыми, как в примере; при чтении порядок пар не важен, `Id` сравниваются без учёта регистра.
Повтор `Id` — предупреждение, используется первое значение; запись заменяет первое и удаляет повторы.

## Чтение: `XDataV2.Read` → `ObjectValues`

Разбор не бросает исключений: любые повреждения становятся предупреждениями (`Warnings`), а
данные сохраняются как есть. Значение (`ObjectValue`) получает состояние по разделу 6.5:

| `State` | Когда | `Value` |
| --- | --- | --- |
| `Typed` | код и значение соответствуют типу схемы | `string`, `double`, `int`, `bool`; строки таблицы — `Rows` |
| `NotInSchema` | `Id` нет в NOD (или колонки нет в таблице) | исходное значение строкой, доступно удаление |
| `TypeMismatch` | код не совпадает с типом (`1000` вместо `1040`, `1070 . 5` для `Boolean`) | строкой; запись нового значения приводит к типу схемы |
| `UnknownEnumKey` | ключа нет в справочнике (если не `allowCustom`) | ключ, с предупреждением |
| `UnknownType` | тип схемы неизвестен этой версии плагина (раздел 11) | строкой, только чтение |

Также предупреждения выдаются для: превышения 16 КБ, формата `Newer`, повторного раздела
`BobrovXDATA`, незакрытого/лишнего `{`/`}`, значения без `Id`, пары без значения, `DEVICE_ID` не в
виде GUID, шаблона, которого нет в схеме. Ключ строки `Table` — колонка `key` или первая колонка
типа `String` (раздел 4.2).

`XDataV2.FindDuplicateDeviceIds` находит одинаковые `DEVICE_ID` в выделении (`COPY`, `ARRAY`,
буфер обмена): исходный ID остаётся у объекта с меньшим handle (handle сравниваются как
шестнадцатеричные числа: `2` < `A` < `1F`), остальные отмечаются как копии.

## Запись: `XDataPatch` для v2

Одна операция `SelectionEdit` меняет одну пару или одну строку таблицы:

| Операция | Действие |
| --- | --- |
| `SetParameter(id, value)` | Приводит значение к типу (`"2,5"` → `1040 . 2.5`, `true`/`"Да"` → `1070 . 1`), проверяет его правилами схемы (`min`/`max`, `maxLength`, ключ ENUM, 255 байт) и заменяет пару или добавляет её в конец. `Table`, `CalculatedString`, параметры вне схемы и неизвестного типа не задаются. |
| `RemoveParameter(id)` | Удаляет пару, в том числе вне схемы (раздел 6.5). |
| `SetTableCell(table, rowKey, column, value)` | Меняет ячейку строки с ключом; если строки у объекта нет, она добавляется (как у материалов в групповом редактировании). |
| `AddTableRow(table, cells)` / `DeleteTableRow(table, rowKey)` | Добавляет строку (ключ обязателен и уникален) / удаляет строку по ключу. |
| `SetTemplate(id)` | Записывает `TEMPLATE`, значения не удаляются (раздел 6.6); у объекта без `DEVICE_ID` создаётся новый GUID (6.4). Пустой `id` удаляет `TEMPLATE`. |
| `NewDeviceId()` | Каждому объекту группы — свой новый GUID. |

Все прочие пары, значения без `Id`, другие RegApp до и после раздела и XRecord объекта
сохраняются в исходном порядке (XRecord — по ссылке, поэтому транзакция их не перезаписывает).
Запись v2 отклоняется, если схема не загружена (сначала `VELEC_SCHEMA_IMPORT`), формат `V1`
или `Newer`, раздел `BobrovXDATA` повторяется или список повреждён.

## Лимиты и групповая запись

`XDataWriter` сначала строит новые данные для всех объектов выделения, затем открывает объекты
на запись. Если хотя бы один объект нарушает лимит раздела 6.3, операция отменяется для всей группы:

- строка `1000` длиннее 255 байт UTF-8;
- оценка размера XDATA объекта (`XDataV2.EstimateSize`, все RegApp) больше 16 383 байт и больше,
  чем до операции (объект, уже превысивший оценку, можно уменьшать). Оценка завышена: код группы
  2 байта, строка — 3 байта + UTF-8, `1070` — 2, `1071` — 4, `1040` — 8, точки — 24.

Групповая запись одного поля меняет только это поле: у каждого объекта остаются свои прочие
значения. Объекты, у которых значение уже совпадает, не открываются на запись.

## Кэш значений

`ObjectValuesCache` — один на документ (`AutoCadSchemaCaches.ValuesFor`), handle → `ObjectValues`:

- XDATA объекта разбирается один раз; повторный выбор того же набора (новый снимок с теми же
  значениями) берёт запись из кэша — `ParseCount` не растёт. Совпадение проверяется по значениям,
  поэтому изменения другими командами, Undo/Redo и `entmod` замечаются при следующем чтении выделения.
- Запись через палитру удаляет из кэша только изменённые объекты.
- Новая схема (импорт, изменение `VELEC`, Undo/Redo NOD) очищает весь кэш.
- Размер ограничен LRU (10 000 объектов).

`SelectionViewModel.Values` — значения выделения из кэша; предупреждения v2 и дубли `DEVICE_ID`
показываются в «Диагностике» объекта. С `XDATAPALETTE_TRACE=1` строка «Прочитано объектов…»
выводит размер кэша и счётчик разборов. Отображение значений в VST — этап 5.
