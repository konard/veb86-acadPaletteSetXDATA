# Схема параметров в NOD и команды импорта/экспорта (TZXDATA, этап 2)

Этап 2 из [TZXDATA](../TZXDATA.md): схема из `schema.json` (этап 1, [parameter-schema.md](parameter-schema.md))
хранится в словаре именованных объектов чертежа и после импорта не зависит от JSON.
Формат записей, сравнение, отчёт и кэш реализованы в `Core` и тестируются без AutoCAD;
слой AutoCAD только переносит записи в `DBDictionary`/`Xrecord`.

| Файл | Назначение |
| --- | --- |
| `src/AcadPaletteSetXData.Core/SchemaNod.cs` | Модель ⇄ записи `VELEC/INFO\|PARAMETERS\|ENUMS\|TEMPLATES` (`DataRecord`), `INFO`, хэш, проверка повреждений. |
| `src/AcadPaletteSetXData.Core/SchemaImport.cs` | План импорта «Объединить»/«Заменить», конфликты типов, список изменений, текст отчёта. |
| `src/AcadPaletteSetXData.Core/SchemaUsage.cs` | Подсчёт объектов, использующих параметры и шаблоны (XDATA v2 и v1), для отчёта. |
| `src/AcadPaletteSetXData.Core/SchemaNodWriter.cs` | `ISchemaNodTransaction` и запись только изменённых записей одной транзакцией. |
| `src/AcadPaletteSetXData.Core/SchemaCache.cs` | Кэш схемы документа: словари по `Id` без учёта регистра, счётчик загрузок. |
| `src/AcadPaletteSetXData.AutoCAD/AutoCadSchemaNod.cs` | Чтение `NOD/VELEC` и транзакция записи (блокировка документа + одна транзакция). |
| `src/AcadPaletteSetXData.AutoCAD/SchemaCommands.cs` | Команды `VELEC_SCHEMA_IMPORT` и `VELEC_SCHEMA_EXPORT`. |
| `src/AcadPaletteSetXData.AutoCAD/AutoCadSchemaCaches.cs` | Кэш на документ и его сброс по событиям AutoCAD. |
| `examples/tzxdata-stage2-nod.lsp` | `VELECDUMP` — вывод записей `VELEC` для ручной проверки. |

## Структура

```text
NOD
└── VELEC                         DBDictionary
    ├── INFO                      Xrecord: storage, hash, importedAt, source, mode + корневые поля JSON
    ├── PARAMETERS                DBDictionary
    │   └── <Id параметра>        Xrecord: order + поля объекта parameters[i]
    ├── ENUMS                     DBDictionary
    │   └── <Id справочника>      Xrecord: order + поля объекта enums[i]
    └── TEMPLATES                 DBDictionary
        └── <Id шаблона>          Xrecord: order + поля объекта templates[i]
```

Один объект схемы — один Xrecord, ключ словаря — его `Id`. Порядок объектов восстанавливается
по системному полю `order`. `INFO` содержит все корневые поля `schema.json`, кроме списков
(`format`, `version` и неизвестные поля), поэтому экспорт возвращает их без потерь.
Посторонние записи внутри `VELEC` читаются с предупреждением и не изменяются при импорте.

## Кодирование Xrecord

Xrecord — последовательность полей «имя + значение»; поля совпадают с полями канонического
объекта `schema.json`, поэтому новые и неизвестные поля сохраняются как есть.

| Код | Содержимое |
| --- | --- |
| `1` | Имя поля JSON (обычный текст до 240 байт UTF-8). |
| `303` | Имя поля необычного вида (пустое, длинное, со спецсимволами) — фрагменты строки JSON. |
| `2` | Имя системного поля: `order`, `storage`, `hash`, `importedAt`, `source`, `mode`. |
| `300` | Текст; длинный текст — несколько фрагментов по ≤ 240 байт без разрыва суррогатных пар. |
| `90` | Целое `int32` в канонической записи (`1`, `-7`). |
| `40` | Вещественное, если запись JSON восстанавливается точно (≤ 15 значащих цифр, `2.5`, `0.1`). |
| `290` | `true`/`false`. |
| `302` | Компактный JSON: списки, объекты, `null`, числа вида `2.50`/`1e300`, текст, который DXF мог бы изменить. |

Текст хранится кодом `300` только если DXF прочитает его без изменений: без управляющих
символов, одиночных суррогатов, пробелов по краям, `\` (последовательности `\U+XXXX`, `\M+`)
и `^` (`^J`). Иначе значение пишется как строка JSON кодом `302`, где `\` и `^` заменены
на `\u005c` и `\u005e`. Так схема одинаково переживает сохранение в DWG и DXF.

`INFO.storage` — версия формата хранения (сейчас `1`), `INFO.hash` — SHA-256 канонического
`schema.json`. Отсутствие обязательных частей, неизвестная версия хранения, повреждённые
фрагменты и несовпадение хэша дают ошибки `InvalidStorage`: схема считается повреждённой,
экспорт отказывается её записывать, а импорт разрешает только «Заменить».

## `VELEC_SCHEMA_IMPORT`

1. Выбор `schema.json`; файл проверяется (раздел 4.5). При ошибках импорт прекращается.
2. Если в чертеже уже есть схема — выбор режима:
   - **Объединить** — новые объекты добавляются, совпавшие по `Id` (без учёта регистра)
     заменяются объектом из файла, остальные остаются; корневые поля берутся из файла.
   - **Заменить** — схема чертежа становится равной файлу.
3. Конфликт типа при «Объединить» (`Power: String` в чертеже, `Double` в файле) не применяется
   молча: `Оставить` / `Заменить` для всех или `Поштучно`. По умолчанию — оставить.
4. Отчёт: добавлено/изменено/удалено по разделам, конфликты типов, объекты, которые удаляются
   из схемы, но используются в XDATA примитивов (модель, листы, блоки), результат проверки
   итоговой схемы. При ошибках итоговой схемы (например, шаблон ссылается на удалённый
   параметр) запись не выполняется.
5. Подтверждение `Да/Нет` (по умолчанию `Нет`).
6. Запись: одна блокировка документа, одна транзакция, один шаг Undo. Пишутся только
   изменившиеся Xrecord и `INFO`; отсутствующие в итоговой схеме удаляются. Если схема уже
   совпадает с файлом, чертёж не изменяется (не меняются даже дата и источник в `INFO`).

Пример отчёта:

```text
Режим: Заменить
Параметры: добавлено 1, изменено 1, удалено 1
  ~ power (тип String → Double) [используется объектами: 1]
  + New
  - Old [используется объектами: 2]
Справочники: добавлено 0, изменено 0, удалено 0
Шаблоны: добавлено 0, изменено 1, удалено 0
  ~ X [используется объектами: 1]
Конфликты типов: 1
  power: в чертеже String, в файле Double — заменить [используется объектами: 1]
Удаляются из схемы, но используются объектами: 1
  Параметр Old — объектов: 2
  Значения в объектах сохраняются и показываются как «Не описаны в схеме».
```

## `VELEC_SCHEMA_EXPORT`

Читает схему из NOD (через кэш) и записывает канонический `schema.json` (UTF-8, без BOM).
Чертёж не изменяется. Если схемы нет или она повреждена, файл не создаётся.

## Кэш схемы

`SchemaCache` — один на документ (`AutoCadSchemaCaches.For(document)`), строится из NOD при
первом обращении. Сбрасывается:

- при `Database.ObjectModified`/`ObjectErased`/`ObjectUnappended`/`ObjectReappended` для NOD,
  `VELEC`, его словарей и Xrecord (по ObjectId, сохранённым при загрузке) и для объектов,
  владелец которых — один из этих словарей;
- после завершения или отмены `U`, `UNDO`, `REDO`, `MREDO`;
- после импорта;
- при закрытии документа (кэш удаляется вместе с подписками).

Каждый документ имеет собственный кэш, поэтому переключение документов не смешивает схемы.
`XDATAPALETTE_TRACE=1` выводит сообщения о загрузке и сбросе кэша.

## Проверка

Автотесты (`tests/AcadPaletteSetXData.Core.Tests`):

- `SchemaNodTests` — побайтовый round-trip `examples/schema.json` через записи, коды значений,
  тексты с `\U+`, `^J`, переводом строки и суррогатами, длинные тексты, неизвестные поля,
  значения в виде, который возвращает AutoCAD, повреждения, а также сохранение в текст DXF
  и чтение обратно (`SchemaSurvivesADxfTextRoundTrip`).
- `SchemaImportTests` — «Объединить»/«Заменить», конфликты, неизменность входных данных,
  проверка итоговой схемы, точный текст отчёта, подсчёт использования.
- `SchemaNodWriterTests` — одна фиксация, запись только изменённого, удаление, смена регистра
  `Id`, отказ при ошибках, кэш.

Проверка в AutoCAD (DWG/DXF, `U`, экспорт) — раздел «TZXDATA, этап 2» в [autocad-verification.md](autocad-verification.md).
